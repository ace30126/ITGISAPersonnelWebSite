## 한 줄 정의

요구사항 분석은 사용자의 요구를 도출해 목표를 정하고 해결 방식을 결정하는 개발의 첫 단계이며, 도출과 분석과 명세와 확인의 절차로 진행된다.

## 왜 시험에 나오나

기능과 비기능 요구사항의 구분, 정형과 비정형 명세 기법의 구분, 검토 방법 세 가지의 정의가 고정 출제된다.

## 핵심

- 기능 요구사항은 시스템이 무엇을 하는가를, 비기능 요구사항은 성능과 보안과 품질과 안전을 다룬다.
- 요구사항 분석에는 비용과 일정의 제약 설정, 타당성 조사, 요구사항 정의 문서화가 들어간다.

| 검토 방법 | 정의로 주어지는 문구 |
|---|---|
| 동료 검토 | 작성자가 명세서를 설명하고 이해관계자가 들으며 결함을 발견 |
| 워크스루 | 회의 전에 명세서를 미리 배포해 사전 검토한 뒤 짧은 회의로 오류를 조기 검출 |
| 인스펙션 | 작성자를 제외한 검토 전문가들이 명세서를 확인하며 결함을 발견 |

- 정형 명세 기법은 수학적 원리와 표기법을 쓰며 Z와 VDM과 페트리넷이 속한다. 표현이 간결하지만 이해가 어렵다.
- 비정형 명세 기법은 자연어를 기반으로 서술하며 이해가 쉽지만 일관성이 떨어진다.

## 헷갈리는 지점

- 워크스루와 인스펙션은 다르다. 사전 배포 후 짧은 회의면 워크스루, 작성자를 제외한 전문가 검토면 인스펙션이다. 두 정의를 맞바꾼 보기가 반복 출제된다.
- Z 기법은 정형 명세 기법이다. 비정형 명세에서 Z를 사용한다는 서술은 오답이다.
- 화면이 3초 이내에 보여야 한다는 성능 조건은 비기능 요구사항이다. 조회와 입금과 송금 같은 동작 목록이 기능 요구사항이다.
- 설계 명세서 작성은 요구사항 분석이 아니라 그다음 명세 단계의 일이다.
- 요구사항 분석은 개발의 첫 단계다. 사용 중 발견되는 오류를 정리하는 단계라는 서술은 유지보수와 섞은 오답이다.
- 사용자의 요구는 예외가 많아 구조화가 어렵다. 예외가 거의 없어 열거가 쉽다는 서술은 방향이 반대다.

## 기출 패턴

구분 문항은 구체적인 요구 문장 하나를 주고 기능인지 비기능인지 고르게 한다. 검토 방법 문항은 세 정의를 뒤섞어 옳은 짝을 고르게 하며 리팩토링이나 CASE 도구를 검토 방법인 것처럼 넣는다. 명세 기법 문항은 정형과 비정형의 특징 중 하나만 뒤집는다.

## 퀴즈
- q: 검토 회의 전에 명세서를 미리 배포해 사전 검토한 뒤 짧은 회의로 오류를 찾는 방법은?
  choices: [동료 검토, 워크스루, 인스펙션, 빌드 검증]
  a: 2
  why: 사전 배포와 짧은 회의가 워크스루의 정의다. 인스펙션은 작성자를 제외한 전문가가 상세히 조사하는 방식이라 절차가 다르다.
- q: 비기능 요구사항에 해당하는 것은?
  choices: [모든 화면이 3초 이내에 표시된다, 계좌 이체 기능을 제공한다, 회원 가입 기능을 제공한다, 잔액 조회 기능을 제공한다]
  a: 1
  why: 응답 시간은 성능이므로 비기능 요구사항이다. 나머지 셋은 시스템이 수행할 동작을 말하므로 기능 요구사항이다.
- q: 요구사항 개발 프로세스의 순서로 옳은 것은?
  choices: [분석 → 도출 → 명세 → 확인, 도출 → 분석 → 명세 → 확인, 도출 → 명세 → 분석 → 확인, 명세 → 도출 → 분석 → 확인]
  a: 2
  why: 도출로 요구를 모으고 분석한 뒤 명세하고 확인한다. 명세가 분석보다 앞서는 배열은 설계 명세서를 분석 단계로 착각하게 만드는 오답이다.
